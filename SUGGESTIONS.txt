More ideas added 2026-10-19, after v3.2.16. Newest ideas added 2026-10-20, after v3.3.23.
Ordered roughly by how much I'd recommend doing them first. Each item says why.
Finished items are marked [x] DONE, paused ones [ ] ON HOLD. The second list is numbered from 0.1 so it doesn't
clash with the first list's numbers; the more ideas carry on from 0.26, the newest from 0.41.

OLD TABLETS
-----------

[x] DONE 0.41 Pick files on Android 4.4. (v4.0.0)
    Android 4.4's WebView never asks the app for a file picker, so "Restore", "Open a recipe file" and a recipe photo
    did nothing there. On Android 4.4 the bridge now says canPickFile(), and pickFile(accept) opens Android's own picker
    (photos only for a photo) and hands the file back as {name, type, base64}. The page turns it into a Blob with a name
    and text() (UTF-8 without TextDecoder) and uses it like a picked file (openFilePicker, useChosenFile). Android 5.0
    and newer, iOS and the desktop keep the WebView's own picker. Tested in tests/e2e/phone-pick-file.mjs (restore with
    accented text, a recipe file, a photo, cancelling); the picker opens in the Android 4.4 emulator.

[x] DONE 0.42 Test the old-tablet page on Android 4.4 on GitHub, on every push. (v4.0.1)
    The Android workflow has a job "old-tablet": it builds legacy/ and a debug APK, boots the Android 4.4 emulator
    (WebView 30) and runs android/legacy-check.sh. That opens the app, connects to its WebView's DevTools and runs
    tests/legacy-device/smoke.mjs: reload with the console on, then every page, the Tools tabs, a recipe page, Settings,
    the item dialog, the recipe editor, cook mode, Dutch and back, and the dark theme (the dark stylesheet swapped in,
    the page really dark). Any script error or failed step fails the job; screenshots of each page in light and dark
    are kept as the artifact "Old-tablet-screenshots". Locally, `bash android/test-apk.sh <debug apk> 19` runs the same
    check (Android 4.4–6, debug builds), and the emulator image now has Node for it.

[x] DONE 0.43 Old browsers on the server version get the old-tablet page too. (v4.0.2)
    The Docker image builds legacy/ in a stage of its own (the dev dependencies stay out of the image) and the server
    serves it (/legacy/…, plain names only) with the .woff fonts. A few lines of old-style JavaScript at the top of
    index.html try ?. and ??; a browser that can't (older than Chrome 80 or Safari 13.1) goes to legacy/index.html,
    which uses the shared kitchen, live updates and the household PIN like any page. The phone apps never redirect
    (they pick the page themselves), and the legacy build leaves the check out of its own page.
    tests/e2e/old-browser-redirect.mjs: a new browser stays, an "old" one (a Function that refuses ?.) is sent to the
    legacy page, and an item added there reaches the server. Not tried with a real old browser yet: the old tablet's
    Chrome 81 still gets the normal app.

[x] DONE 0.44 Read aloud and right-to-left on old tablets. (v4.0.3)
    Read aloud works on Android 4.4: the bridge uses the older speak() and a Locale made from the language code there
    (forLanguageTag and the speak() with an utterance id are Android 5.0), so canSpeak() is always true. The legacy
    build now makes four stylesheets, light and dark each left-to-right and right-to-left (postcss-logical with either
    direction; the grid fallbacks put their gaps on the right side for each), and tools/legacy/dom.js swaps them when
    the app sets data-theme or dir. The legacy-build test and the Android 4.4 check switch to Arabic and look for the
    right-to-left sheet with the sidebar's space on the right. Read aloud itself is not tried on a real tablet.

0.45 A lighter old-tablet page.
    The old-tablet copy is about 1.2 MB of scripts before the app shows anything (app/cook.js alone grows to 245 kB,
    mostly the \p{L} letter classes written out), and an old tablet is slow to read it. Minify the legacy files,
    write each letter class once instead of in every pattern, and time the start on the emulator before and after.


EVERYDAY USE
------------

0.46 A kitchen screen.
    A tablet on the wall or the counter is used from a distance, but every page is made for reading up close. A
    "Kitchen screen" view with only the big things (today's meal, running timers, what to use soon, the shopping
    count), large type, the screen kept on and dimmed at night, and one tap back to the full app.

0.47 "Plan my week" fills the empty days.
    The planner already puts recipes that use something from Use soon first, but you still pick each day. One button
    could suggest a recipe for every empty day: first what uses up Use soon, then what needs the least shopping,
    without repeating a recent meal. Each suggestion can be kept or swapped, and nothing is planned until you say so.

0.48 "Use by" and "best before".
    Every date is treated the same now, but a "use by" date on meat or fish means "don't eat it after", and a "best
    before" date on pasta only means it may be less good. Let a package date say which it is, keep the strict
    warning for "use by", and show past "best before" items as "check it" instead of "expired", so less good food is
    thrown away.

0.49 Allergens and diets.
    The ingredient catalog knows what each ingredient is, so it could also know gluten, milk, eggs, nuts, fish, meat.
    Recipes would get small labels ("contains nuts", "vegetarian") and the Recipes page a filter, which helps a
    household with an allergy or a guest who doesn't eat meat. Only a hint: a recipe's text can always hide something.

0.50 The shopping list learns your shop.
    The list is in a general supermarket order, but every shop is laid out differently. The order in which items
    are ticked off says how your shop is laid out; after a few trips the groups could follow that order, per shop if
    there's more than one.

0.51 What waste costs.
    "This month" counts what was thrown away. An optional price on items (remembered from the last time) would turn
    that into money ("thrown away this month: about €14"), which is what makes people change habits, and would give
    the shopping list a rough total.


PHONE, DESKTOP AND SERVER
-------------------------

0.52 Share into Goodstock.
    On a phone, a recipe is usually found in the browser. Goodstock could appear in Android's and iOS's share menu:
    a shared web address opens Import with that address, shared text goes into "Fill in from text", and a shared
    list of words can go onto the shopping list.

0.53 The meal plan in your calendar.
    The plan lives only in Goodstock. The server could offer it as a calendar feed (/api/plan.ics, with a token in
    the address like the PIN's), so the phone's own calendar shows "Dinner: Chicken curry" and the household sees
    the week without opening the app.

0.54 Check the rest of the app for accessibility.
    From 0.40: cook mode, the scan and put-away dialogs and touch-target sizes aren't checked yet. Cook mode matters

    when a photo is unusually large, and show the kitchen's size in Settings → Your data.

[x] DONE 0.26 The shopping list counts amounts. (v3.3.3)
    "Make the shopping list" adds up the week's meals that aren't cooked yet per ingredient, compares that with the
    stock in the stored item's unit (grams against kilos, millilitres against litres) and lists only what is short:
    "Flour 650 g · Pancakes, Bread". Under a kilo or a litre it says grams or millilitres. Where the amounts can't be
    compared ("1 bunch" against "200 g", a teaspoon against grams) the item counts as enough, as before.
    Found on the way: stock matching found short names from other languages inside longer ones (Dutch "ei" in
    Portuguese "leite" and "queijo", Turkish "un" in Romanian "pătrunjel"), so milk, cheese and salt counted as
    "Eggs" in stock and parsley as "Flour". A name now only counts inside another when it is longer than three letters.

[x] DONE 0.27 Thaw reminders the evening before. (v3.3.4)
    The Inventory page has a "Take out of the freezer" box (above Use soon) when today's or tomorrow's meals need
    something that is only in the freezer, with nothing of it in the fridge or cupboard: "Chicken · for Chicken curry
    tomorrow · Freezer". "Moved to the fridge" moves it there (the first fridge location), drops the frozen-on date and
    gives it two days, with Undo. With use-soon reminders on, the phone apps and the desktop app schedule a
    notification at 19:00 the evening before ("1 thing to take out of the freezer: Chicken for Chicken curry"); the
    browser version sends it after 19:00 while it is open, once a day.

[x] DONE 0.28 "What can I make with it?" from Use soon. (v3.3.5)
    Every Use soon row has "Recipe ideas ✨". It opens the Recipes page searched for that item (so your own recipes
    with it come first, found in any language through the catalog) and "Recipes from the web with spinach" below,
    looked up on TheMealDB by the catalog's English name. "All ideas" goes back to the usual ideas from your cooking
    history. The "Try using it in …" links stay next to it.

[x] DONE 0.29 A quick stocktake, one place at a time. (v3.3.6)
    "Check a place" on the Inventory page lists the storage places with their item count and when each was last
    checked ("Freezer · 1 item · checked 5 weeks ago", "never checked"). Picking one shows its items as big rows with
    Still there, Less (the edit dialog; saving counts as checked) and Gone (Used up or Thrown away, which goes into the
    month overview like any removal, with Undo). "Done" saves today's date for that place in the kitchen (state.checks,
    merged between devices like the other lists).

[x] DONE 0.30 Learn shelf life from what gets thrown away. (v3.3.7)
    Items now remember when they came into the kitchen (addedOn, set only for new ones: older items don't count), and
    "Thrown away" records how many days it was kept and in which kind of storage. Once the same thing in the same
    storage has been thrown away three times, by the median a day or more before its estimate, the Inventory page shows
    "Learned from your kitchen: Carrots · in the fridge. Thrown away 3 times, usually after 18 days. The estimate is
    21 days." with "Use 18 days" or "Keep 21 days". An accepted time is used for new items of that kind (package dates
    still win); either answer stops the question. Times are only ever made shorter. Answers are shared with the
    household (state.shelfLife).

[x] DONE 0.35 Desktop: keep hosting with the window closed. (v3.3.12)

[x] DONE 0.17 Easy HTTPS (biggest win for the server version). (v3.2.7)
    An optional "https" service in docker-compose.yml and compose.yaml (Compose profile "https", so it stays off
    unless asked for): Caddy built from https/ (Dockerfile + Caddyfile, so Portainer Git stacks need nothing on
    the host). HTTPS_HOST is the devices' address (an IP works); by default Caddy makes its own certificate
    authority, which each device installs once from http://<host>:8485/goodstock-root.crt; with HTTPS_CERT set to
    an email address and a public domain it gets a Let's Encrypt certificate. HTTPS on port 8443, live events
    passed straight through. README → HTTPS has the steps per device; tools/check-https.sh tests it in Docker and
    runs on GitHub. Plain http on 8484 stays, for the phone apps (they don't trust a home-made certificate).
    STILL FOR YOU: install the certificate on the kitchen tablet and check voice and notifications in Chrome 81.

[x] DONE 0.18 Automatic backups on the server. (v3.2.8)
    Before the first save of each day the server copies the kitchen to /data/backups/state-YYYY-MM-DD.json. Before
    a save that removes more than half of the inventory and recipes (from at least six) it also makes a safety
    copy, "…-before-HHMM.json", so a mistaken Wipe or a bad sync during the day loses nothing. The newest 14 are
    kept. Settings → Your data lists them (date, counts, "before a big change") with Restore, which asks first and
    then works like restoring a backup file.

[x] DONE 0.19 Restart the container when it is unhealthy. (v3.2.9)
    An "autoheal" service (willfarrell/autoheal 1.2.0) in both Compose files, behind the Compose profile
    "autoheal" instead of commented out: off by default, and in Portainer switched on with one environment
    variable. It watches only containers labelled autoheal-goodstock (the Goodstock service has that label) every
    30 seconds. Tried in Docker: a container that turned unhealthy was restarted within seconds.


LANGUAGES
---------

[x] DONE 0.20 Amounts in the steps for the remaining languages. (v3.2.10)
    Russian, Polish, Romanian and Turkish: the amount in brackets after the word, found by its stem so other
    endings match too ("муки" → "Просейте муку (200 г)", "yumurta" → "yumurtaları (3)"). Chinese: before the name
    ("加入2个鸡蛋"). Japanese: in brackets after it ("卵（2個）を"), which reads better there than in front. Names
    are found inside the sentence, also by their catalog names. Ingredient lines may have the amount first or last
    ("Соль — 1 ч. л.", "鸡蛋 2个", "砂糖 大さじ2"); units stay as written. An amount already in the step stays.

[x] DONE 0.21 Right-to-left languages, the layout part. (v3.2.11)
    A language with dir: 'rtl' in LANGUAGES sets <html dir="rtl">. styles.css now uses logical margins, paddings,
    borders and text alignment everywhere (screenshots of every view in English are unchanged), and mirrors the
    positioned parts in a [dir="rtl"] section at the end (Chrome 81 has no inset-inline): the menu moves to the
    right, toggles, timers and dialogs follow. Arrows like → are turned around after each render; ‹ › mirror by
    themselves. What people type (recipes, items, the list) keeps its own direction (unicode-bidi: plaintext), so
    an English recipe stays readable in an Arabic interface. tests/e2e/rtl-layout.mjs checks every view at
    tablet and phone width in a stand-in right-to-left language.
    v3.2.13: Arabic and Hebrew added (938 lines each, machine-written like the others: see 0.5 for a real
    read-through). Also: catalog names for all 63 ingredients, units (غ, مل, كوب, גרם, מ״ל, כף…), storage and
    recipe-heading words, cook-mode times and voice commands, kitchen-tool words (with the small prefixes like
    "ال" and "ה"), amounts in the steps in brackets, sentence splitting without capitals, DeepL, and the iOS
    app's languages. Arabic dates use Western digits, like the amounts in recipes.
